# Dry-Run Revival — 2026-08-06

A full rehearsal of `RUNBOOK.md` against a throwaway Supabase project, using
only the artifacts a trustee would have: the GitHub mirror and the B2 backup
bucket (read-only key). The live Lovable/Supabase project was never touched.

**Result: the runbook works end-to-end, with the corrections now folded into
RUNBOOK.md sections 3, 4, and 4a.** Total effort: well under the runbook's
~3-hour estimate once the fixes below are known.

## Findings (fixes committed to RUNBOOK.md)

1. **`db push` fails on a fresh project.** Migration `20251206020240_*`
   hardcodes an INSERT into `user_roles` for admin id `8b7e8511-…`, which
   doesn't exist in a fresh `auth.users`. Pre-create that auth user (or
   restore all auth users first), then `db push` resumes cleanly.
   → RUNBOOK 3.

2. **The backup contains no password hashes.** `auth/users.ndjson.gz` has no
   `encrypted_password` field for any of the 83 users — the backup function
   uses the admin `listUsers` API, which never returns hashes. RUNBOOK 4a
   previously claimed passwords were preserved; it was wrong. On a real
   revival, email/password users must reset their passwords (making working
   auth SMTP — RUNBOOK 5a — a hard prerequisite); Google OAuth users
   re-match by email. Optional follow-up: have the backup function dump
   `auth.users` via direct SQL to capture hashes. → RUNBOOK 4a.

3. **REST-based data loading re-fires triggers.** `audit_log` ended at 1,572
   rows (snapshot: 525) and `notifications` at 3,170 (snapshot: 1,011) from
   trigger-generated rows. Loading over direct SQL with
   `session_replication_role = replica` avoids this. → RUNBOOK 4.

4. **The runbook's hardcoded table list was stale.** Several table names no
   longer exist. The reliable approach: load whatever files the snapshot's
   `db/` folder contains, multi-pass with FK-failure retry. → RUNBOOK 4.

5. **Minor:** migrations seed a default `layers` row (count off-by-one vs
   snapshot); `scroll_ai_usage` has no `id` column, so count it with
   `select=*`. → RUNBOOK 4.

## What this proves

- A person with the GitHub mirror + B2 credentials + a Supabase account can
  bring the full schema, all user accounts, and all application data back
  online, and sign-ins work against the restored stack.
- The two revival-blocking risks are both now documented with workarounds:
  the mid-sequence migration failure (finding 1) and the password-loss
  surprise (finding 2).
